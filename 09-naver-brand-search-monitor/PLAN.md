# 네이버 브랜드검색(브검) 모니터링 자동화 PLAN

기준 문서: `SPEC.md`

Google Apps Script는 쓰지 않고, 로컬 Python 스크립트(`collect.py`) 하나로 크롤링·판정·저장·대시보드 생성까지 끝내는 것을 기준으로 합니다. 화면 캡처만 Playwright(헤드리스 Chromium)를 예외적으로 씁니다 — CSS 레이아웃을 픽셀로 렌더링하는 건 표준 라이브러리로는 할 수 없기 때문입니다. 그 외 로직(파싱·해시·DB·대시보드)은 표준 라이브러리만 사용합니다.

## 개발 원칙
- 키워드는 1개로 먼저 전체 파이프라인(크롤링 → 판정 → 저장 → 대시보드)을 검증한 뒤 여러 개로 늘립니다.
- 동일 판정(콘텐츠 해시 동일)이면 자동/수동 관계없이 새 레코드를 만들지 않습니다.
- 모든 실행은 자동이든 수동이든 같은 `collect()` 파이프라인을 거칩니다(분기는 최소화).
- 실행마다 로그를 남겨 실패 원인을 나중에 확인할 수 있게 합니다.

## Phase 1 개발 단위

### P1-01. 프로젝트 골격 및 키워드 관리
- 목표: 서비스가 쓸 파일 구조와 키워드 로딩을 준비합니다.
- 구현 항목
  - `keywords.json` 스키마: `[{"사용여부": "Y", "브랜드명": "...", "등록일": "...", "비고": "..."}]`
  - 없으면 빈 배열로 취급, 있으면 `사용여부== "Y"`인 키워드만 필터링
- 주요 함수: `load_keywords()`
- 완료 기준
  - `keywords.json`이 없어도 에러 없이 빈 목록으로 시작합니다.
  - `사용여부`가 `N`인 키워드는 수집 대상에서 제외됩니다.

### P1-02. SQLite 스키마 초기화
- 목표: `data.db`에 필요한 테이블을 멱등하게 만듭니다.
- 구현 항목
  - `records(id, 수집일시, 최종확인일시, 수집방식, 키워드, 운영여부, 상태, 타이틀, 카피, 서브링크, 상품, 하단스트립, 이미지경로, 원문링크, 콘텐츠해시, 변경내역)` (서브링크/상품/하단스트립은 JSON 배열 문자열)
  - 구버전 `data.db`(옛 `타이틀_카피` 단일 컬럼)를 그대로 열어도 깨지지 않도록, 없는 컬럼은 `ALTER TABLE ADD COLUMN`으로 보강(멱등, 이미 있으면 스킵)
  - `logs(id, 실행일시, 수집방식, 대상키워드수, 신규건수, 변경건수, 미운영전환건수, 동일건수, 오류수, 오류내용)`
- 주요 함수: `init_db()`
- 완료 기준: 여러 번 실행해도 기존 데이터가 지워지지 않고 테이블이 정상 존재합니다.

### P1-03. 네이버 브랜드검색 크롤러 + 화면 캡처 + 필드 추출
- 목표: 키워드로 통합검색을 Playwright로 렌더링해 브랜드검색(`brand_search`) 영역 유무와 4개 항목(타이틀/서브링크/상품/하단스트립)을 텍스트로 파싱하는 동시에, SNS 소식을 제외한 영역 전체를 스크린샷으로 캡처합니다.
- 구현 항목
  - Playwright 헤드리스 Chromium으로 `page.goto()` → `page.content()`로 렌더링된 HTML 확보
  - `brand_search` 블록 존재 여부로 운영여부 판정
  - 타이틀(`main_title`)·카피(`main_desc`)·원문링크는 단일 값으로, 서브링크(`link_button_item`)·상품(`product_item`)·하단스트립(`light_plus_item`)은 목록으로 정규식 추출
  - 블록 내부에서 "브랜드 SNS 소식"(`m_brand_channel`) 콘텐츠는 텍스트 파싱과 화면 캡처 양쪽 모두에서 제외
  - 운영중이면 SNS 소식 블록을 JS로 숨긴 뒤 `.brand_search` 요소 전체를 PNG 스크린샷으로 캡처
- 주요 함수: `parse_brand_search(html_text)`, `capture_brand_search_image(page)`
- 완료 기준
  - 실제 브랜드검색을 운영 중인 키워드로 테스트하면 타이틀/카피/원문링크와 서브링크·상품·하단스트립 목록이 실제 화면과 일치하게 추출되고, 캡처 이미지에 본문·서브링크·상품 리스트·하단 스트립이 모두 보이며 SNS 소식은 보이지 않습니다.
  - 미운영 키워드는 빈 결과(운영여부=미운영)를 반환하고 캡처를 시도하지 않습니다.

### P1-04. 콘텐츠 해시 + 변경 판정 + 변경 필드 라벨링
- 목표: 이번 수집 결과를 직전 레코드와 비교해 신규/변경/동일/미운영전환으로 분류하고, "변경"이면 5개 필드 중 무엇이 바뀌었는지 라벨을 남깁니다.
- 구현 항목
  - `hashlib.sha256(캡처_이미지_바이트)`로 해시 생성. 신규/변경/동일/미운영전환 분류는 이 해시로만 판단(이미지 전체 비교라 어떤 하위 요소가 바뀌어도 빠짐없이 잡힘)
  - 해당 키워드의 최신 레코드 유무·해시 비교로 4가지 케이스 분류
  - "변경"으로 분류되면 타이틀/카피/서브링크/상품/하단스트립 5개 필드를 직전 레코드와 각각 비교해 달라진 항목의 라벨 목록을 만듦. 5개 필드가 전부 같은데 이미지 해시만 다르면(예: 상품 썸네일 이미지만 교체) 빈 목록을 반환하고, 호출부에서 "세부 항목은 동일 (이미지·레이아웃 차이로 추정)"으로 대체 표기
- 주요 함수: `build_hash(image_bytes)`, `classify(prev_record, current)`, `diff_fields(prev_record, parsed)`
- 완료 기준
  - 같은 캡처 이미지는 항상 같은 해시를 만듭니다.
  - `test_collect.py`로 4가지 판정 케이스와 `diff_fields`의 3가지 케이스(필드 1개만 다름/목록 필드만 다름/전부 동일)를 각각 확인합니다.
  - 통합 시나리오(가짜 크롤러로 상품 리스트만 바꿔 2회 연속 수집)에서 `records.변경내역`에 `상품(product_item)`만 정확히 남는 것을 확인합니다.

### P1-05. 캡처 이미지 저장
- 목표: 신규/변경 건만 캡처 이미지를 로컬에 저장합니다.
- 구현 항목
  - `images/{키워드}/{수집일시}.png` 경로로 저장 (Playwright 스크린샷 기본 포맷)
  - 미운영·동일 건은 저장하지 않음
- 주요 함수: `save_screenshot(image_bytes, keyword, collected_at)`
- 완료 기준: 신규/변경 건에서만 파일이 생성되고, 나머지 케이스는 파일이 생기지 않습니다.

### P1-06. 레코드 저장 (자동/수동 공통)
- 목표: 판정 결과를 `records`에 반영합니다.
- 구현 항목
  - 신규/변경/미운영전환 → `INSERT` (최신 레코드가 되어 조회 시 자동으로 맨 위에 옴, `ORDER BY 수집일시 DESC`)
  - 동일 → `INSERT` 없이 해당 키워드 최신 레코드의 `최종확인일시`만 `UPDATE`
- 주요 함수: `insert_record(record)`, `touch_last_checked(keyword, checked_at)`
- 완료 기준
  - 동일 판정을 여러 번 반복해도 레코드 수는 늘지 않고 `최종확인일시`만 갱신됩니다.
  - 최신 레코드 조회 시 가장 최근 변경 건이 항상 첫 행입니다.

### P1-07. 자동/수동 실행 진입점
- 목표: 같은 파이프라인을 자동수집·수동수집 두 방식으로 실행할 수 있게 합니다.
- 구현 항목
  - `collect(mode)`: P1-01~P1-06을 순서대로 실행하는 공통 파이프라인
  - CLI: 인자 없이 실행하면 자동수집(`mode="자동"`), `--manual`이면 수동수집(`mode="수동"`)
  - 자동수집은 "어제 09시~오늘 09시", 수동수집은 "당일 자정~실행 시점"을 관측 범위로 `records.수집방식`에 함께 기록(실제 크롤링은 매번 최신 상태 스냅샷이며, 범위는 기록용 라벨)
- 주요 함수: `collect(mode)`, `main()`
- 완료 기준: `python collect.py`와 `python collect.py --manual` 모두 정상 동작하고, `records.수집방식`이 각각 올바르게 기록됩니다.

### P1-08. 로그 기록
- 목표: 실행 결과를 나중에 확인할 수 있게 남깁니다.
- 구현 항목: 대상 키워드 수, 신규/변경/미운영전환/동일 건수, 오류 수·내용 집계 후 `logs`에 기록
- 주요 함수: `write_log(summary)`
- 완료 기준: 실행마다 건수 합계가 실제 처리된 키워드 수와 일치합니다.

### P1-09. 대시보드 정적 HTML 생성
- 목표: 수집 기록을 날짜별로 묶고, 그 안에서 브랜드 개수만큼 컬럼을 나눠 한 화면에서 비교할 수 있게 만듭니다.
- 구현 항목
  - `records`를 최신순으로 읽어 `수집일시`의 날짜(`YYYY-MM-DD`)로 그룹핑(`by_date: date -> {키워드: row}`), 날짜별로 키워드당 최신 1건만 사용
  - 컬럼 수는 `load_keywords()`(현재 등록·사용중인 브랜드) 개수를 그대로 씀 — 키워드가 늘거나 줄면 컬럼도 자동으로 맞춰짐
  - 레이아웃: 날짜 섹션(`<h2>YYYY-MM-DD 수집</h2>`) 아래 `grid-template-columns: repeat(n, 1fr)`로 브랜드 컬럼을 나열. 각 컬럼은 세로(column) 정렬로 캡처 이미지가 위, 텍스트가 아래
  - 그 날짜에 해당 브랜드의 새 레코드가 없으면(동일 판정) 빈 칸 템플릿으로 표시
  - 브랜드 칸 구성: 이미지(`<img>`) + 키워드 + 운영여부/상태 배지 + (변경 건이면) 바뀐 부분 안내문 + 타이틀/카피/서브링크/상품/하단스트립 5개 필드(라벨 위·값 아래, `<code>클래스명</code>` 병기) + 수집일시 + 최종확인일시 + 원문 링크
  - 서브링크/상품/하단스트립은 pill(둥근 배지) 목록으로, 값이 없으면 "-"로 표시
  - 상단 바: 등록된 키워드별 운영 상태 배지(운영중/미운영/대기중, `get_latest_record` 기준, `.kw-status-group`은 라벨-배지묶음 column 정렬·배지들끼리는 `.kw-status-row`로 row 정렬) + 새 키워드 입력 필드 + 수동 수집 버튼
    - 두 버튼은 `fetch('/api/keywords', ...)` / `fetch('/api/collect', ...)`로 P1-12 서버 API를 호출한다(클립보드 복사 방식은 P1-12에서 실제 동작으로 교체됨). 서버가 없으면(연결 실패) 화면에 안내 문구를 표시한다.
  - 대시보드/로그 히스토리 탭: 순수 JS로 두 `<div>`(`#view-dashboard`, `#view-logs`)의 `hidden` 속성을 토글. 로그 히스토리는 `logs` 테이블을 최신순 `<table>`로 렌더링(로그는 원래 시계열 표 데이터라 `<table>` 사용에 문제없음 — 브랜드 기록 카드에 `<table>`을 안 쓴 것과 별개)
- 주요 함수: `build_dashboard()`, `_render_brand_cell()`, `_text_field_html()`, `_pill_field_html()`, `_keyword_status_html()`, `_logs_table_html()`
- 완료 기준
  - 브라우저로 `dashboard/index.html`을 열면 날짜 섹션이 최신순으로 위에서부터 나오고, 각 섹션 안에 브랜드 컬럼이 정확히 `keywords.json`에 등록된 개수만큼 보입니다.
  - 각 필드가 클래스명과 함께 라벨링되어 세로로 표시되고, "변경" 건에는 바뀐 부분이 문장으로 표기됩니다.
  - 그날 수집되지 않은(동일 처리된) 브랜드는 빈 칸으로 표시되고 에러 없이 렌더링됩니다.
  - 상단 배지가 각 키워드의 최신 운영여부와 일치합니다.
  - "로그 히스토리" 탭을 누르면 대시보드가 숨겨지고 `logs` 표가 보이며, "대시보드" 탭으로 되돌아갈 수 있습니다.

### P1-12. 로컬 대시보드 서버 (키워드 추가·삭제·수동 수집 버튼 실동작)
- 목표: 대시보드의 "키워드 추가"/"× 삭제"/"지금 수동 수집 실행"이 클립보드 복사가 아니라 실제로 `keywords.json`을 갱신하고 `collect()`를 실행하게 한다.
- 구현 항목 (`server.py`, 표준 라이브러리 `http.server`만 사용)
  - `ThreadingHTTPServer` + `SimpleHTTPRequestHandler`를 확장해 `directory=BASE_DIR`로 정적 파일(대시보드, 이미지) 서빙
  - 기본 `127.0.0.1:8765`(외부 노출 없음). `--host`/`--port` CLI 인자로 바꿀 수 있고, `--host 0.0.0.0`이면 같은 네트워크의 다른 PC도 접속 가능(그 경우 `_lan_ip()`로 이 PC의 LAN IP를 추정해 접속 주소를 안내). `/` 요청은 `/dashboard/index.html`로 302 리다이렉트
  - `POST /api/keywords`: body의 `브랜드명`을 검증(빈 값/중복 거부) 후 `keywords.json`에 append, `build_dashboard()`로 대시보드 즉시 재생성, JSON 응답
  - `POST /api/keywords/delete`: body의 `브랜드명`과 일치하는 항목을 `keywords.json`에서 제거(없으면 404), 대시보드 즉시 재생성. `data.db`의 과거 `records`는 건드리지 않는다(삭제 = 화면에서 빠지는 것이지 이력 삭제가 아님).
  - `POST /api/collect`: `collect("수동")`을 그 자리에서 호출하고 결과 건수를 JSON으로 응답(완료까지 요청이 대기)
  - `keywords.json` 읽기/쓰기 로직은 `_load_keywords_raw()`/`_save_keywords_raw()`로 공통화해 추가·삭제 핸들러가 중복 없이 재사용
  - 상단 키워드 배지마다 `×` 버튼(`data-kw` 속성) 렌더링(`_keyword_status_html`), 클릭 시 이벤트 위임으로 `confirm()` 확인 후 `/api/keywords/delete` 호출
  - PAGE_TEMPLATE의 버튼 JS를 `fetch` 기반으로 구현(`addKeyword()`, `runManualCollect()`, 삭제는 전역 클릭 리스너), 진행 중 버튼 비활성화 + 상태 문구, 성공 시 `location.reload()`, 연결 실패 시 "서버를 실행하세요" 안내
- 완료 기준
  - `python3 server.py` 실행 후 `http://127.0.0.1:8765/`로 들어가면 대시보드가 보이고(파일 직접 열 때와 달리 이미지도 정상 로드됨 — `../images/...` 상대경로가 서버 루트 기준으로 풀림), 키워드 입력 후 버튼을 누르면 `keywords.json`에 실제로 추가되고 페이지가 새로고침되며 컬럼 수가 늘어납니다.
  - 배지의 `×`를 누르고 확인하면 `keywords.json`에서 제거되고, 새로고침 후 해당 브랜드의 `brand-col`이 화면에서 사라지며 컬럼 수도 줄어듭니다. `data.db`의 기존 레코드는 남아있습니다.
  - 수동 수집 버튼을 누르면 실제로 Playwright가 실행되어 결과가 반영된 화면으로 새로고침됩니다.
  - 서버를 끈 채 파일을 직접 열면 세 기능 모두 실패 안내만 뜨고, 나머지 조회 기능은 그대로 동작합니다.
  - 이미 등록된 키워드를 다시 추가하면 409, 없는 키워드를 삭제하면 404로 거부됩니다.
